# Goal Checker Agent

Проверка формулировки цели на соответствие действующим приказам.
Требования хранятся графом в Neo4j, языковая модель (vLLM) определяет,
какие проверяемые атрибуты присутствуют в тексте цели, Cypher-запросы
находят сработавшие запреты и невыполненные требования.

## Архитектура

```
web (nginx :3000) ──► api :8080           редактор каталога и проверка целей
api (FastAPI :8080) ─┬─► Neo4j :7687      каталог, поиск нарушений
                     └─► vLLM :8000       извлечение атрибутов из цели
seeder (разовый)   ──► Neo4j              схема + миграции из neo4j/init/
export_graph.py    ◄── Neo4j              выгрузка графа обратно в seed.cypher
```

Веб-интерфейс общается только с API: прямого подключения к Neo4j из браузера
больше нет, вместе с ним из кода страницы ушёл и пароль базы.

## Модель данных

```
(:Order {orderId, number, title, date, status})
  -[:CONTAINS]->   (:Clause {clauseId, code, text})
  -[:DEFINES]->    (:Rule {ruleId, type, description, checkInstruction})
  -[:APPLIES_TO]-> (:CheckTarget {name, description})

(:Rule)-[:HAS_EXAMPLE]->(:ViolationExample {exampleId, text, isViolation})
(:Clause)-[:REFERENCES]->(:Clause)
```

`Rule.type` задаёт направление проверки:

| type | Нарушение возникает, когда атрибут |
|---|---|
| `PROHIBITION` | **присутствует** в цели |
| `REQUIREMENT` | **отсутствует** в цели |

У `Order`, `Clause`, `Rule`, `CheckTarget` и `ViolationExample` есть свойство
`status` (`active` / `archived`). Все запросы проверки фильтруют по нему через
`coalesce(x.status, 'active')`, поэтому узлы, заведённые до появления статуса,
остаются активными.

`CheckTarget` — единственный источник истины по проверяемым атрибутам.
Промпт для модели строится из `CheckTarget.description` во время выполнения,
поэтому новый атрибут добавляется правкой графа, а не кода.

### Описание атрибута — обязательно

У атрибута без `description` модель получает в промпте только имя, без
критерия, и системно перестаёт его распознавать. Внешне это выглядит как
«правило срабатывает всегда»: атрибут не найден → требование не выполнено.
Поэтому `/ready` отдаёт 503, пока есть атрибуты без описания.

### Написание имён

Уникальность `CheckTarget.name` не защищает от двойников: для Neo4j
`«срок исполнения»` и `«срок_исполнения»` — разные узлы. Если правило висит
на одном написании, а модель вернула другое, получается ложное нарушение.

Защита двухслойная: агент сопоставляет имена по нормализованной форме
(регистр, пробелы, дефисы, «ё») и при совпадении засчитывает **все**
написания сразу, а `/ready` и поле `notes` в ответе сообщают о самих
дублях, чтобы их свели к одному узлу, а не жили с ними.

## Запуск

В `.env` должны быть заданы `NEO4J_PASSWORD`, `VLLM_MODEL` и `HF_TOKEN`
(полный список — в таблице ниже).

```bash
docker compose up -d --build
```

Порядок подъёма задан через `depends_on`: `neo4j` → `seeder` → `api`.
API стартует только после того, как сидер успешно отработал, а vLLM
прошёл healthcheck (загрузка весов 8B-модели занимает несколько минут,
поэтому у неё `start_period: 900s`).

| Сервис | Адрес |
|---|---|
| API | http://localhost:8080 |
| Swagger | http://localhost:8080/docs |
| Редактор каталога | http://localhost:3000 |
| Neo4j Browser | http://localhost:7474 |

Для запуска без GPU укажите внешний OpenAI-совместимый эндпоинт
через `VLLM_URL` и поднимайте стек без сервиса `vllm`.

## Эндпоинты

```bash
curl -s localhost:8080/health          # liveness
curl -s localhost:8080/ready           # readiness + диагностика графа
curl -s localhost:8080/check-targets   # словарь проверяемых атрибутов

curl -s localhost:8080/check-goal \
  -H 'Content-Type: application/json' \
  -d '{"goal": "Снизить долю просроченных заявок до 5% к 31.12.2025"}'
```

`/ready` отдаёт 503 и список `problems`, если Neo4j недоступен, граф пуст,
есть двойники атрибутов, атрибуты без описания, атрибуты без правил или
правила без атрибутов — то есть в любой ситуации, когда проверка целей
будет молча неполной.

Ответ `/check-goal`:

```json
{
  "goal": "...",
  "status": "ALLOWED | VIOLATIONS_FOUND | NEEDS_MANUAL_REVIEW",
  "allowed": false,
  "detected_attributes": ["срок_исполнения", "измеримость"],
  "violations": [
    {
      "order_number": "ПР-01",
      "order_title": "О порядке постановки целей",
      "clause_code": "1.1",
      "clause_text": "...",
      "rule_id": "R-1.1",
      "rule_text": "...",
      "check_instruction": "Проверь, указан ли в тексте цели проект...",
      "violation_type": "MISSING_REQUIREMENT",
      "attribute": "проект",
      "example_kind": "correct",
      "examples": ["..."]
    }
  ],
  "notes": []
}
```

`notes` — не декоративное поле. Туда попадают атрибуты, которых нет
в словаре графа, и обнаруженные двойники написаний: это причины, по
которым результат проверки может быть неполным.

Оба типа нарушений возвращаются с одинаковым набором полей; различать их
следует по `violation_type` и `example_kind` (`violation` — так делать нельзя,
`correct` — образец правильной формулировки).

### Режим отказа: fail-closed

Если извлечь атрибуты не удалось (модель недоступна, вернула не JSON,
словарь `CheckTarget` пуст), ответ будет `status: NEEDS_MANUAL_REVIEW`
и `allowed: false`, а причина — в `notes`. Проверка соответствия
никогда не «разрешает» цель из-за собственного сбоя.

## Веб-интерфейс

`http://localhost:3000` — редактор каталога. Четыре вкладки:

| Вкладка | Что делает |
|---|---|
| Приказы и пункты | дерево приказ → пункт → правило → атрибуты и примеры; создание, правка, архивирование, удаление; поиск по всему дереву |
| Атрибуты | словарь `:CheckTarget` с описаниями; видно, какие правила ссылаются на атрибут и у каких нет описания |
| Проверка цели | прогон формулировки через `/check-goal` с разбором нарушений |
| Диагностика | вывод `/ready`: что мешает графу считаться готовым |

Адрес API по умолчанию — тот же хост, порт 8080; переопределяется параметром
`?api=http://host:port`, поэтому интерфейс работает и через SSH-туннель.

### Удаление — двухшаговое

«Удалить» никогда не означает «потерять с первого клика»:

1. **В архив** — узел получает `status: "archived"`, выпадает из проверок
   (все запросы фильтруют по статусу), но остаётся в графе. Обратимо кнопкой «Вернуть».
2. **Удалить** — физическое удаление, доступно **только для архивированного**
   узла и только после подтверждения, где показано, что именно уйдёт
   (сколько пунктов, правил, примеров).

Архивирование любого узла на пути `Приказ → Пункт → Правило → Атрибут`
отключает всё, что ниже: проверка идёт по цепочке целиком.

Атрибут нельзя удалить, пока на него ссылается хотя бы одно правило —
иначе правило осталось бы висеть в пустоте и молча не срабатывать.

### Защита от двойников на входе

При создании атрибута имя сравнивается по нормализованной форме, поэтому
завести «срок исполнения» рядом с «срок_исполнения» через интерфейс
невозможно — API вернёт 409 с указанием существующего написания.

## Эндпоинты каталога

```
GET    /catalog/tree?include_archived=false     всё дерево одним ответом
GET    /catalog/check-targets                   словарь атрибутов

POST   /catalog/orders                          PATCH /catalog/orders/{id}
POST   /catalog/orders/{id}/status              DELETE /catalog/orders/{id}
POST   /catalog/clauses                         PATCH /catalog/clauses/{id}
POST   /catalog/clauses/{id}/status             DELETE /catalog/clauses/{id}
POST   /catalog/rules                           PATCH /catalog/rules/{id}
PUT    /catalog/rules/{id}/targets              привязка к атрибутам
POST   /catalog/rules/{id}/status               DELETE /catalog/rules/{id}
POST   /catalog/check-targets                   PATCH /catalog/check-targets/{name}
POST   /catalog/check-targets/{name}/status     DELETE /catalog/check-targets/{name}
POST   /catalog/examples                        PATCH /catalog/examples/{id}
                                                DELETE /catalog/examples/{id}
```

`404` — узла нет, `409` — операция противоречит состоянию графа
(двойник по написанию, удаление неархивированного узла, используемый атрибут).

## Данные: база — источник истины

`neo4j/init/seed.cypher` содержит только схему (ограничения и индексы) и
маркер `// ---------- Данные ----------`. Сами приказы не пишутся в файл
руками — они выгружаются из живой базы:

```bash
docker compose exec api python export_graph.py --output /init/seed.cypher
```

Скрипт снимает приказы, пункты, правила, атрибуты, примеры и связи и
дописывает в файл идемпотентный `MERGE`-скрипт со стабильным порядком
строк. После этого `docker compose up` воспроизводит граф один в один,
а `git diff` показывает, что именно поменялось в нормативке.

Посмотреть выгрузку, ничего не записывая:

```bash
docker compose exec api python export_graph.py --stdout
```

### Миграции

Разовые правки данных лежат в `neo4j/init/migrations/` и запускаются
тем же сидером через `SEED_FILE`:

```bash
# перед любой миграцией — дамп
docker compose exec neo4j neo4j-admin database dump neo4j --to-stdout > backup.dump

docker compose run --rm \
  -e SEED_FILE=/init/migrations/001_cleanup_demo_data.cypher seeder
docker compose run --rm \
  -e SEED_FILE=/init/migrations/002_check_target_descriptions.cypher seeder
```

| Миграция | Что делает |
|---|---|
| `001_cleanup_demo_data` | удаляет демо-приказы ПР-2024-15 / ПР-2024-22, сводит двойники `CheckTarget`, чистит осиротевшие атрибуты и примеры |
| `002_check_target_descriptions` | проставляет описания атрибутам `проект` и `срок_исполнения`; шаблон для остальных внутри файла |

### Порядок приведения базы в порядок

```bash
docker compose exec neo4j neo4j-admin database dump neo4j --to-stdout > backup.dump
docker compose run --rm -e SEED_FILE=/init/migrations/001_cleanup_demo_data.cypher seeder
docker compose run --rm -e SEED_FILE=/init/migrations/002_check_target_descriptions.cypher seeder
curl -s localhost:8080/ready | python3 -m json.tool   # что ещё осталось починить
# дописать описания оставшимся атрибутам, затем зафиксировать состояние:
docker compose exec api python export_graph.py --output /init/seed.cypher
git diff neo4j/init/seed.cypher
```

## Тесты

```bash
cd api
pip install -r requirements-dev.txt
pytest
```

Тесты не требуют ни Neo4j, ни vLLM — внешние зависимости подменяются.
Покрыты: разбор ответа модели (блоки `<think>`, markdown-ограждения,
мусор), сопоставление имён атрибутов при расхождении написания,
поведение fail-closed, разбиение Cypher-скрипта, идемпотентность и
стабильность выгрузки, диагностика в `/ready`, сборка дерева каталога,
запрет на двойников и на удаление неархивированных узлов — то есть ровно
те места, где расхождение схемы и кода уже приводило к молчаливым отказам.

Интерфейс отдельно проверен браузерным прогоном (Playwright) по сценарию
«создать атрибут → приказ → пункт → правило → пример → архив → удаление
→ проверка цели», включая экранирование пользовательского ввода.

## Известные ограничения

- `/check-goal` и все эндпоинты `/catalog/*` не аутентифицированы и не
  ограничены по частоте. Редактор каталога доступен любому, кто открыл
  страницу, — до выхода за пределы доверенной сети нужна авторизация.
- Текст цели попадает в промпт без экранирования — возможна prompt injection.
- Агент засчитывает атрибут по нормализованному имени, но это лечение
  симптома: двойники в графе всё равно нужно сводить, иначе часть правил
  останется на «мёртвом» узле.
- Версии Python-зависимостей зафиксированы вручную; для полной
  воспроизводимости стоит перейти на lock-файл (`pip-compile`, `uv lock`).
