# Архитектура и модель данных

[← README](../README.md)

## Архитектура

```
web (nginx :3000) ──► api :8080           редактор каталога и проверка целей; /api проксирует nginx
api (FastAPI :8080) ─┬─► Neo4j :7687      каталог, поиск нарушений, реестр пользователей
                     ├─► vLLM :8000       извлечение атрибутов из цели
                     └─► Keycloak        проверка токена входа (ключи realm-а)
web (браузер) ─────► Keycloak            вход пользователя (OpenID Connect, PKCE)
seeder (разовый)   ──► Neo4j              схема, данные (в пустой каталог) и миграции из neo4j/init/
export_graph.py    ◄── Neo4j              выгрузка каталога в neo4j/init/data.cypher
```

Веб-интерфейс общается только с API: прямого подключения к Neo4j из браузера
больше нет, вместе с ним из кода страницы ушёл и пароль базы. Запросы идут
на тот же origin (`/api`), nginx интерфейса передаёт их сервису `api`; сам
порт API, как и порты Neo4j и vLLM, слушает только `127.0.0.1`. Вход, роли
и журнал аудита описаны в [доступе и безопасности](security.md).

## Модель данных

```
(:Order {orderId, number, title, date, status})
  -[:CONTAINS]->   (:Clause {clauseId, code, text})
  -[:DEFINES]->    (:Rule {ruleId, type, description, checkInstruction, studentsOnly})
  -[:APPLIES_TO]-> (:CheckTarget {name, description})

(:Rule)-[:HAS_EXAMPLE]->(:ViolationExample {exampleId, text, isViolation})
(:Clause)-[:REFERENCES]->(:Clause)

(:Department {departmentId, name, status})
(:Rule)-[:ONLY_IN]->(:Department)
(:Department)-[:HAS_JOB_DESCRIPTION]->(:JobDescription {jobDescriptionId, title, text, status,
                                                       duties, dutiesReviewed, dutiesStatus, dutiesError})

(:User {login, role, status, displayName, sub, createdAt, createdBy, lastLoginAt, tourSeenAt})
(:Setting {key, value, updatedAt, updatedBy})
(:ApiKey {keyId, name, hash, createdAt, createdBy, lastUsedAt})
(:SmartScore {goalHash, scores, updatedAt})
(:CheckRecord {at, ms, status, …})
(:CatalogVersion {id: "catalog", version})
(:CatalogLock {id})
```

`:User` — реестр пользователей интерфейса: кому можно войти и с какой
ролью (пароля в нём нет). `sub` — учётная запись Keycloak, к которой запись
привязана при первом входе ([подробнее](security.md#привязка-к-учётной-записи-keycloak)).
К каталогу реестр не относится: в выгрузку `data.cypher` не попадает,
полный сброс каталога его не трогает, операции над произвольным узлом
(`/catalog/nodes/*`) его не видят. То же относится к `:Setting`
(переключатели раздела «Настройки»), `:ApiKey` (ключи доступа внешних
систем), `:SmartScore` ([оценки по SMART](#оценка-по-smart)), `:CheckRecord`
([история проверок](#история-проверок-и-мониторинг)), `:CatalogVersion`
([версия каталога](#версия-каталога-и-кэш-ответов)) и `:CatalogLock`
(ниже); в выгрузку и раздел «Граф» они не попадают.

Правки каталога, которые меняют несколько связей сразу, — замена атрибутов
правила, области действия, перекрёстных ссылок, перенос, создание правила со
связями, проверка «используется ли» перед удалением, — идут одной
транзакцией с блокировкой узла: параллельная правка не оставит граф
наполовину изменённым.

Операции вида «проверить, занято ли, и записать» сериализуются замком на
понятие, а не на узел: служебным узлом `(:CatalogLock {id})`, единственным
на `id` (ограничение уникальности в `seed.cypher`). Так защищены проверка
двойников атрибута при создании, переименовании и сведении и подбор
свободного идентификатора при создании пунктов, правил, примеров
и инструкций: два одновременных запроса не заведут двойника и не получат
`409` вместо свободного суффикса. Ограничение создаёт сидер, поэтому он
должен отработать до старта API — compose так и делает.

`Rule.type` задаёт направление проверки:

| type | Нарушение возникает, когда атрибут |
|---|---|
| `PROHIBITION` | **присутствует** в цели |
| `REQUIREMENT` | **отсутствует** в цели |

У `Order`, `Clause`, `Rule`, `CheckTarget` и `ViolationExample` есть свойство
`status` (`active` / `archived`). Все запросы проверки фильтруют по нему через
`coalesce(x.status, 'active')`, поэтому узлы, заведённые до появления статуса,
остаются активными.

`CheckTarget` — единственный источник истины по проверяемым атрибутам.
Промпт для модели строится из `CheckTarget.description` во время выполнения,
поэтому новый атрибут добавляется правкой графа, а не кода.

## Примеры в промпте

По умолчанию модель решает, есть ли атрибут в цели, только по его
описанию. Настройка «Примеры в промпте» добавляет под атрибутом примеры
из каталога — до заданного настройкой «Примеров на атрибут» числа каждого вида:

```
- "проект" — в цели явно назван проект, программа или инициатива…
    есть: «В рамках проекта «Альфа» разработать API для интеграции до 01.06.2025»
    нет: «Реализовать требования по автоматизации процесса в системе 1С:KPI»
```

Пример в каталоге относится к правилу, а промпту нужен ответ про атрибут,
и однозначен он не всегда:

| Правило | Пример | Что говорит про атрибуты правила |
|---|---|---|
| требование | корректный | все присутствуют — «есть» |
| требование | нарушение | не хватает хотя бы одного; идёт в «нет», только если атрибут у правила один |
| запрет | корректный | ни одного нет — «нет» |
| запрет | нарушение | есть хотя бы один; идёт в «есть», только если атрибут у правила один |

Неоднозначные примеры в промпт не попадают. Исправить ошибку модели при
включённой настройке можно, не переписывая описание атрибута: достаточно
добавить правилу пример — ту цель, на которой она ошиблась. Эффект
настройки измеряется [проверкой примеров](web-ui.md#проверка-примеров-на-модели).

## Советчик по графу

Ответ модели про атрибут зависит от двух вещей в графе: описания атрибута
и, при включённых примерах в промпте, примеров правил. Когда редактор не
согласен с ответом по цели — атрибут найден, а не должен был, или наоборот, —
подбирать формулировку описания вручную не нужно: советчик (`api/advisor.py`)
делает это за него.

1. Тем же запросом, что и настоящая проверка, но мимо кэша, убеждается, что
   модель действительно отвечает не так, как ждёт редактор.
2. Просит модель переписать описание атрибута: в запрос идут текущее
   описание, примеры каталога, цель, ответ модели и обоснование редактора.
3. Проверяет предложение на самой цели. Ответ не изменился — следующая
   попытка с указанием, что уже пробовали (до `ADVICE_MAX_ATTEMPTS`, по
   умолчанию 3).
4. С подошедшим описанием прогоняет примеры каталога, по которым ответ про
   атрибут известен (до `ADVICE_MAX_EXAMPLES`, по умолчанию 40): правка под
   одну цель не должна ломать остальные. Пример, на котором модель ошибалась
   и раньше, поломкой не считается.
5. Называет правила, которым цель можно добавить примером, — только
   с единственным атрибутом: у остальных пример неоднозначен (см. таблицу выше).

Граф советчик не меняет. Предложение применяет редактор: правкой свойства
`description` и созданием примера. Запросы советчика в историю и кэш проверок
не попадают; прогон по примерам идёт пакетом в общей очереди к модели и не
занимает слоты ручных проверок.

У атрибута, определяемого по должностным инструкциям, описание — критерий
сравнения: советчику нужно подразделение с загруженными инструкциями, а
проверки на примерах и предложения примеров для него нет.

Советчик работает на той же модели, что и проверка. Предложенное описание —
черновик: проверено, что оно даёт нужный ответ на цели и не ломает примеры,
но не то, что оно верно передаёт смысл приказа, — это решает редактор.

## Разграничение по подразделениям

Какое правило в каком подразделении действует — часть приказа, поэтому
это хранится в графе, а не в коде и не в вызывающей системе. Подразделения
плоские, без иерархии; у каждого есть название и `departmentId` — тот
идентификатор, который кадровая система передаёт в запросе проверки.

| Связь от правила | Что означает |
|---|---|
| нет связей | правило действует для всех подразделений |
| `ONLY_IN` | правило действует только в перечисленных подразделениях |

Пример: проект обязателен только в УЦТ и АГД — у правила две связи
`ONLY_IN`. Для цели любого другого подразделения это правило не
проверяется вовсе.

Состояний два: правило в подразделении либо действует, либо нет.
Исключений («действует, но не применяется») нет: связи `EXCEPT_IN`,
оставшиеся от прежней версии, проверка не учитывает, о них сообщают
«Замечания», а убирает миграция `005_drop_exceptions`.

### Если подразделение неизвестно

Отказ в сторону строгости, как и при сбое модели: если `department_id`
не передан, не найден в графе или подразделение в архиве, применяются
**все** правила — включая ограниченные через `ONLY_IN`. Причина пишется
в `notes`. Неизвестное подразделение
не должно получать более мягкий набор правил, чем известное.

По той же причине ограничение `ONLY_IN` учитывается независимо от статуса
подразделения, а удалить подразделение, на которое ссылаются правила,
нельзя: иначе ограничение исчезло бы вместе со связью, и правило молча
стало бы действовать для всех.

## Правила только для студентов

Часть пунктов приказов касается только студентов (практикантов, стажёров):
например, цель студента обязана называть наставника. Такое правило помечается
свойством `Rule.studentsOnly = true`; у остальных правил свойства нет или
оно `false`.

Кто ставит цель, знает вызывающая система, поэтому признак приходит
в запросе проверки булевым полем `is_student` — рядом с `department_id`.
Запросы проверки отбирают правила условием
`coalesce($is_student, true) OR NOT coalesce(r.studentsOnly, false)`:

| `is_student` | Правила с `studentsOnly` |
|---|---|
| `true` | проверяются |
| `false` | пропускаются |
| не передан | проверяются — отказ в сторону строгости, причина в `notes` |

Отбор по подразделению и по студенту независимы: правило может быть
одновременно «только в УЦТ» и «только для студентов». Ответ из кэша
берётся только при том же признаке: та же цель сотрудника и студента —
разные наборы правил.

## Должностные инструкции

Часть требований нельзя проверить по одному тексту цели. Пункт 3.5 запрещает
цели, дублирующие должностные обязанности, — для этого цель нужно сравнить
с должностными инструкциями.

Инструкции хранятся у подразделения (`:JobDescription`, загружаются в разделе
«Подразделения»). Атрибут со свойством `source = "job_descriptions"` в общий
промпт извлечения не попадает: агент отдельным запросом сравнивает цель со
всеми действующими инструкциями подразделения, а критерием служит
`CheckTarget.description`. Дальше атрибут участвует в правилах как обычный:
пункт 3.5 — это запрет (`PROHIBITION`) на таком атрибуте, со своей
областью действия и примерами. Найденные обязанности
возвращаются в нарушении полем `matched_duties`.

При загрузке или правке текста инструкции модель один раз выписывает из него
список обязанностей (`JobDescription.duties`). Цель сравнивается с этим
списком, а не с полным текстом: запрос короче в разы, и все должности
подразделения помещаются в один запрос. Выписка — несколько запросов подряд
(таймаут каждого — `DUTIES_TIMEOUT_SECONDS`, потолок ответа —
`DUTIES_MAX_TOKENS`), поэтому она идёт в фоне: узел создаётся сразу
с `dutiesStatus = pending`, пул из `DUTIES_WORKERS` потоков (1 или 2)
выписывает обязанности и ставит `ready` или `error` с причиной
в `dutiesError` ([API](api.md#должностные-инструкции-и-обязанности)).
Итог не записывается, если текст за это время поменяли; сбой Neo4j при
записи итога повторяется до 3 раз. Потоки выписки — daemon: остановка API
идущую выписку не ждёт, а оборванные выписки при следующем старте
переводятся в `error`. `pending`, у которого в процессе нет задачи (итог так
и не записался), при следующем `GET` инструкции переводится в `error`
(«итог не сохранился, запустите заново»), а `extract-duties` перезапускает
такую выписку без перезапуска API — API работает одним процессом, чужих
идущих выписок не бывает.

Готовый список показывается редактору на проверку (`dutiesReviewed`);
неподтверждённый список уже участвует в проверках и виден в «Замечаниях».
Если модель не ответила, инструкция остаётся без списка и сравнение идёт
по полному тексту.

Пунктов, опирающихся на инструкции, может быть несколько: каждому — свой
атрибут со своим критерием. Каждый такой атрибут — отдельный запрос к модели
на цель; он идёт одновременно с извлечением обычных атрибутов. В один запрос
уходит до `JOB_TEXT_MAX_CHARS` символов (по умолчанию 24000 — под окно vLLM
`VLLM_MAX_MODEL_LEN` в 16384 токена; меняйте их вместе); что не поместилось —
уходит следующим запросом, а отдельный текст длиннее предела сравнивается
не целиком, о чём пишется в `notes`.

Инструкции подразделения и правила на таких атрибутах проверка читает из
графа не на каждую цель: в пакете цели одного подразделения идут подряд,
и прочитанное помнится столько, сколько задано настройкой «Кэш должностных
инструкций» (по умолчанию 60 с, `JOB_DESCRIPTIONS_CACHE_TTL_SECONDS`).
Любая правка каталога через API этот кэш сбрасывает, так что загруженная
инструкция участвует уже в следующей проверке; срок важен только для правок
базы в обход сервиса.

Сравнение выполняется, только если в подразделении действует правило на
таком атрибуте. Сравнения по разным атрибутам и группам инструкций одной
ручной проверки идут параллельно. Совпадение засчитывается, только если
приведённая моделью обязанность дословно (без учёта регистра и пробелов)
есть в той инструкции, которую модель назвала; инструкция ищется по
`jobDescriptionId`, а у старых узлов без него — по названию. «Совпадает»
без такой обязанности считается сбоем сравнения.

Если сравнить не удалось — подразделение неизвестно, инструкции
не загружены, модель не ответила, — цель не разрешается: при отсутствии
других нарушений статус `NEEDS_MANUAL_REVIEW`, причина в `notes`. Требование
(`REQUIREMENT`) на таком атрибуте при сбое не превращается в нарушение
«атрибута нет», а тоже уходит на ручную проверку. Такие ответы не кэшируются,
даже если у цели есть другие нарушения. Подразделения без инструкций
показывает диагностика.

## Оценка по SMART

Кроме пунктов приказов, цель оценивается по методологии SMART: конкретная,
измеримая, достижимая, значимая, ограниченная во времени. Это отдельный
запрос к модели (`agent.assess_smart`), он не зависит от словаря атрибутов
и идёт одновременно с извлечением. Модель отвечает по JSON-схеме: для каждого
из пяти критериев оценка 0–100 и пояснение одним предложением; критерии
уходят системным сообщением, цель — пользовательским, как и в остальных
запросах.

Оценка — справка автору цели, а не правило: на статус проверки она не
влияет, в нарушения не попадает, советчик её не трогает. Если модель не
ответила, в ответе `smart: null` и причина в `notes`, а проверка по приказам
идёт как обычно. Настройка `smartCheck` выключает запрос, `smartCheckBulk` —
только в пакетной проверке; обе входят в число настроек, сбрасывающих кэш
готовых ответов. В кэше готовых ответов оценка не хранится: она
подставляется при каждой выдаче из своего кэша (ниже), поэтому сбой оценки
не закрепляется вместе с ответом. В интерфейсе оценка
показана пятью кругами под вердиктом: заполнение круга — оценка, цвет —
её уровень, под кругом — пояснение.

### Одна формулировка — одна оценка

Модель при нулевой температуре не обещает одинаковых чисел на повторный
запрос, а оценка зависит только от текста цели. Поэтому она живёт отдельно
от готовых ответов проверки (`agent.smart_score`) и переспрашивается у модели
только тогда, когда формулировку ещё не оценивали:

1. **Память процесса** — `metrics.smart_scores`, ключ — текст цели со
   схлопнутыми пробелами и обрезанными краями (регистр сохраняется).
   Подразделение и признак студента в ключ не входят: та же цель в двух
   подразделениях или в пакете из повторов оценивается один раз, даже если
   запросы идут одновременно — второй ждёт результата первого.
   Запись живёт `SMART_CACHE_TTL_SECONDS` (по умолчанию сутки, `0` — без
   срока), кэш ограничен `CHECK_CACHE_MAX_ENTRIES` записями; правка каталога
   (`metrics.catalog_changed`) его не трогает, сбрасывает его смена `smartCheck`.
2. **Граф** — узел `(:SmartScore {goalHash, scores, updatedAt})`: оценка
   переживает перезапуск API. `goalHash` — SHA-256 от нормализованной цели
   вместе с текстом запроса к модели, поэтому смена критериев или инструкции
   в коде обесценивает старые записи сама: они просто перестают находиться.
   При промахе в памяти граф читается до обращения к модели, новая оценка
   записывается в него после. Недоступный граф оценку не ломает — она
   остаётся в памяти процесса. К каталогу узлы не относятся: в выгрузку
   не попадают, операции над узлами каталога их не видят. Оценки, которые
   не обновлялись дольше `SMART_SCORE_RETENTION_DAYS` (по умолчанию 365,
   `0` — хранить всегда), удаляются в фоне не чаще раза в сутки — при
   очередной записи оценки. Ограничение уникальности `goalHash`
   (`smart_score_hash_unique`) API заводит сам при первой записи; если
   в базе уже есть повторяющиеся `goalHash`, остаётся обычный индекс,
   а в логе — предупреждение (очистить оценки можно в «Настройках»).
3. **Модель** — только если оценки нет ни там, ни там. Сбой модели не
   запоминается нигде: в ответе `smart: null` с заметкой, а следующая
   проверка той же формулировки спросит модель снова.

Итог: одинаковая формулировка получает одинаковую оценку в пределах срока
хранения в базе, а не только жизни процесса; выдать другую оценку может лишь
очистка `:SmartScore` (кэш `smart` в «Настройках»), истечение срока
хранения, смена промпта в коде или переключение `smartCheck` (оно чистит
память, но не граф).

## Нагрузка: очередь к модели и кэш

Узкое место проверки — модель. Одновременных запросов к ней на весь сервис —
не больше настройки «Предел запросов к модели» (`llmMaxConcurrency`, по
умолчанию `LLM_MAX_CONCURRENCY`); остальные ждут в очереди внутри API
(`api/metrics.py`). Ожидание в очереди не расходует таймаут модели, поэтому
под нагрузкой цели не уходят в «ручную проверку» из-за таймаутов. Пакетной
проверке недоступен «Резерв для ручных проверок» (`llmInteractiveReserve`,
по умолчанию `LLM_INTERACTIVE_RESERVE`) слотов: массовый прогон не
останавливает ручные проверки. Резерв не больше предела минус один: пакету
нужен хотя бы один слот, лишнее обрезается при чтении настроек.

Сколько запросов видеокарта тянет одновременно, зависит от модели и памяти
GPU и подбирается измерением по «Мониторингу», поэтому оба числа — настройки,
а не константы, и действуют на лету. Очередь (`metrics.LlmGate`) — это
`threading.Condition` со счётчиками работающих запросов, всех и пакетных.
Предел и резерв она берёт из настроек и помнит 5 секунд: ждущие потоки
перепроверяют условие раз в секунду по запомненному значению и в граф
не ходят. Сохранение настройки сбрасывает запомненное и будит ждущие потоки
(`gate.reconfigure`): они перечитывают предел и входят, если место
появилось. Уменьшение предела ниже числа работающих запросов ничего
не прерывает — новые запросы ждут, пока работающие не завершатся.
«Мониторинг» показывает действующие предел и резерв.

Ручная проверка и советчик ждут места в очереди не дольше
`LLM_QUEUE_TIMEOUT_SECONDS` (по умолчанию 120 с) и получают `503`
с `Retry-After` (а не «ручную проверку» в ответе), а не держат поток API
без конца; пакет ждёт без предела. Пакетный запрос держит поток API до
конца пакета, поэтому одновременно их принимается не больше
`BULK_MAX_REQUESTS` (по умолчанию 4), сверх — сразу `503` с `Retry-After: 30`.
Потоков для синхронных обработчиков API — `API_THREADS`, по умолчанию
`40 + 2 × llmMaxConcurrency + BULK_MAX_WORKERS + BULK_MAX_REQUESTS`
(не меньше 40): ручная проверка держит поток всё время ожидания, и
стандартных 40 не хватило бы — при занятой модели встали бы вход, каталог
и «Настройки». При увеличении `llmMaxConcurrency` в «Настройках» предел
потоков пересчитывается без перезапуска (только в большую сторону).
`/health` и `/ready` от этого пула не зависят.

В пакете побочные запросы цели (оценка SMART, сравнение с инструкциями)
идут в потоке самого пакета; отдельный пул для них есть только у ручных
проверок, поэтому массовый прогон не занимает его и не мешает резерву.

Соединение с моделью ждётся `LLM_CONNECT_TIMEOUT_SECONDS` (5 с), ответ —
`LLM_TIMEOUT_SECONDS`. Повтор (`LLM_MAX_RETRIES`) — только при ошибке
соединения и ответе 5xx; после таймаута ответа повтора нет: зависшая модель
не ответит и со второго раза.

Предохранитель (`agent._Breaker`) — отдельный для ручных и для пакетных
запросов: зависание на длинных пакетных промптах не отключает ручные
проверки, и наоборот. После `LLM_BREAKER_TIMEOUTS` таймаутов подряд модель
`LLM_BREAKER_SECONDS` секунд не опрашивается: ручные цели сразу уходят на
ручную проверку («модель не отвечает, проверка повторится позже»), пакетные
ждут закрытия, но не дольше `LLM_BREAKER_BULK_WAIT_SECONDS` (300 с) от
начала сбоя. После паузы к модели идёт один пробный запрос: ответ закрывает
предохранитель, таймаут снова размыкает его на паузу; пока пробный идёт,
прочие ручные запросы сразу получают отказ, пакетные ждут. Таймауты выписки
обязанностей и сравнений с инструкциями (длинные промпты) не засчитываются.
`0` выключает предохранитель.

Ответ модели ограничен JSON-схемой (guided decoding vLLM) и длиной
(`LLM_MAX_TOKENS`): имена атрибутов вне словаря и ответы «мимо формата»
исключены, а сбившаяся модель не держит слот. Если сервер явно сообщает,
что не поддерживает сам `response_format` (`json_schema`, `guided_json`),
API сам переходит на разбор свободного текста (`LLM_JSON_MODE=0` —
выключить заранее). Прочие ошибки режим не выключают — в том числе ошибка
компиляции одной схемы (xgrammar, outlines): этот запрос отклонён,
остальные схемы сервер принимает.

К каждому найденному атрибуту модель приводит цитату — дословный фрагмент
цели (настройка `evidenceQuotes`). API сверяет цитату с текстом цели без
учёта регистра и пробелов. Атрибут без подтверждённой цитаты остаётся
найденным (иначе можно было бы пропустить запрет), но цель автоматически не
разрешается и уходит на ручную проверку. Подтверждённые цитаты возвращаются
в `attribute_quotes` и показываются в ответе: приписка вроде «срок указан»
не может засчитать требование незаметно.

### Версия каталога и кэш ответов

Ответ на ту же цель того же подразделения с тем же признаком студента берётся
из кэша в памяти (настройки «Кэш ответов» и «Срок жизни кэша», не больше
`CHECK_CACHE_MAX_ENTRIES` записей). Ключ — SHA-256 цели со схлопнутыми
пробелами, подразделение и признак студента: цели, отличающиеся только
пробелами, делят запись, а `goal` в ответе подставляется как передан.
Одинаковая цель, которая уже проверяется так же (ручная — ручной, пакетная —
пакетной), ждёт эту проверку, а не идёт к модели второй раз; ручная
проверка идущую пакетную не ждёт. Сбои (`NEEDS_MANUAL_REVIEW`)
не кэшируются. Ответ из кэша ручной проверке, чьей оценки SMART нет
в памяти, ждёт оценку не дольше 1 с, иначе выдаётся со `smart: null`
и заметкой, а оценка досчитывается в фоне.

Версия каталога хранится в графе: `(:CatalogVersion {id: "catalog"}).version`.
Её увеличивают любая правка каталога через API и seeder — после загрузки
данных, миграции или `reset_and_load` (данные и миграции он выполняет одной
транзакцией вместе с увеличением версии, так что API не видит каталог
загруженным наполовину). Узла версии может не быть (установка до первой
миграции) — это версия 0, и его появление тоже считается сменой. API
сверяет версию раз в 30 секунд и при смене сбрасывает кэш готовых ответов
и справочников. Правка через API увеличивает версию, только если дошла
до операции и удалась или упала непредвиденно: отклонённые запросы
(`403`, `422`, `404`, `409`) кэш не сбрасывают. Поэтому миграция или полный
сброс через seeder видны проверкам не позже чем через 30 секунд, и чистить
кэш руками после них не нужно. Ручная правка в Neo4j Browser версию
не меняет: она станет видна через срок жизни кэша, после его очистки
в «Настройках» или после запроса
`MATCH (v:CatalogVersion {id: "catalog"}) SET v.version = v.version + 1`.

Настройки проверки (`:Setting`) читаются из графа не чаще раза в минуту
(запрос — с таймаутом 5 с). Если граф не ответил, служат последние
прочитанные значения, и следующая попытка — не раньше чем через 5 секунд,
чтобы каждая проверка не ждала таймаута заново. Пока настройки не прочитаны
ни разу, защитные переключатели (`maintenance`, `apiKeysEnabled`) считаются
запрещающими.

## История проверок и мониторинг

Каждая проверка оставляет запись `(:CheckRecord {at, ms, status, departmentId,
login, mode, batchId, cached, llmCalls, llmMs, queueMs, violations, goal})`.
Записи пишутся фоновым потоком пачками (`api/history.py`) и хранятся
столько дней, сколько задано настройкой «Срок хранения истории». Если Neo4j
недоступен, записи копятся в памяти (до 50 000, сверх этого теряются самые
старые) и пишутся повторно с растущей паузой от 2 до 60 секунд. При
остановке API идущим запросам даётся 45 секунд доработать, и история
успевает записаться. Повторы одной цели в пакете записываются как ответы
из кэша. Как и `:User`, к каталогу записи не относятся: в выгрузку
не попадают, полный сброс каталога их не трогает.

Раздел «Мониторинг» (только администратор) показывает текущую очередь и
нагрузку — они живут в памяти процесса и после перезапуска начинаются с
нуля, — а также средние показатели за период и историю из графа. Раздел
«Граф» рисует каталог узлами и связями и доступен всем ролям.

### Описание атрибута — обязательно

У атрибута без `description` модель получает в промпте только имя, без
критерия, и системно перестаёт его распознавать. Внешне это выглядит как
«правило срабатывает всегда»: атрибут не найден → требование не выполнено.
Поэтому `/ready` отдаёт 503, пока есть атрибуты без описания.

### Написание имён

Уникальность `CheckTarget.name` не защищает от двойников: для Neo4j
`«срок исполнения»` и `«срок_исполнения»` — разные узлы. Если правило висит
на одном написании, а модель вернула другое, получается ложное нарушение.

Защита двухслойная: агент сопоставляет имена по нормализованной форме
(регистр, пробелы, дефисы, «ё») и при совпадении засчитывает **все**
написания сразу, а `/ready` и поле `notes` в ответе сообщают о самих
дублях, чтобы их свели к одному узлу, а не жили с ними. Сводит их
`POST /catalog/merge-duplicate-targets` (кнопка «Свести двойников»
в «Замечаниях», администратор) той же нормализацией. Сводятся только
двойники с одинаковыми статусом и `source`: остаётся узел с описанием,
затем с большим числом правил; связи правил переносятся на него, удаляются
только сведённые двойники. Группы, где статус или `source` различаются,
возвращаются в `skipped` и сводятся вручную.

## Интерфейс

Веб-интерфейс (`web/`) — статика в образе nginx. `index.html` отдаётся
с `Cache-Control: no-cache`, файлы `/assets/` — с хешем в имени и сроком
кэширования год (`immutable`), отсутствующий файл — `404`, а не
`index.html`; текстовые ответы сжимаются gzip. Поэтому после обновления
браузер сразу получает новую версию.

Запросы к API (`web/src/api/client.ts`) ограничены по времени: диагностика,
граф, сводка и история мониторинга — 180 с, прочее чтение — 30 с,
запись — 120 с, проверка целей и советчик — 610 с (nginx интерфейса ждёт
API до 600 с). Пока тело ответа приходит, срок отсчитывается от последнего
пришедшего куска; оборванный или неразборчивый ответ — ошибка, а не пустые
данные. Вызывающий может отменить запрос (кнопка «Остановить» у пакета).
Общее состояние — в `web/src/state/`: вход и сессия (`auth.tsx`), каталог
(`catalog.tsx`), форма проверки и идущие проверки (`checkForm.tsx`, внутри
`CatalogProvider`, поэтому пакет продолжается при переходе в другой раздел),
черновики форм на время повторного входа (`drafts.ts`). `App` на форму
проверки не подписан: черновик формы ведёт отдельный `CheckDraftKeeper`,
а обучение управляет формой через `useCheckFormControl`, так что ввод цели
не перерисовывает всё приложение. Окна, открытые в момент конца сессии
(редактор свойств, ячейка матрицы, советчик), после входа открывает снова
`web/src/features/RestoredDialogs.tsx`. Счётчики замечаний перечитываются
через 3 секунды после последней правки. Ошибка отрисовки раздела или окна
перехватывается `web/src/ui/ErrorBoundary.tsx` и заменяет только его
карточкой «Ошибка интерфейса».
