# Архитектура и модель данных

[← README](../README.md)

## Архитектура

```
web (nginx :3000) ──► api :8080           редактор каталога и проверка целей; /api проксирует nginx
api (FastAPI :8080) ─┬─► Neo4j :7687      каталог, поиск нарушений, реестр пользователей
                     ├─► vLLM :8000       извлечение атрибутов из цели
                     └─► LDAP / AD        проверка пароля при входе
seeder (разовый)   ──► Neo4j              схема + миграции из neo4j/init/
export_graph.py    ◄── Neo4j              выгрузка графа обратно в seed.cypher
```

Веб-интерфейс общается только с API: прямого подключения к Neo4j из браузера
больше нет, вместе с ним из кода страницы ушёл и пароль базы. Запросы идут
на тот же origin (`/api`), nginx интерфейса передаёт их сервису `api`; сам
порт API, как и порты Neo4j и vLLM, слушает только `127.0.0.1`. Вход, роли
и журнал аудита описаны в [доступе и безопасности](security.md).

## Модель данных

```
(:Order {orderId, number, title, date, status})
  -[:CONTAINS]->   (:Clause {clauseId, code, text})
  -[:DEFINES]->    (:Rule {ruleId, type, description, checkInstruction})
  -[:APPLIES_TO]-> (:CheckTarget {name, description})

(:Rule)-[:HAS_EXAMPLE]->(:ViolationExample {exampleId, text, isViolation})
(:Clause)-[:REFERENCES]->(:Clause)

(:Department {departmentId, name, status})
(:Rule)-[:ONLY_IN]->(:Department)
(:Rule)-[:EXCEPT_IN {status, basis, note}]->(:Department)
(:Department)-[:HAS_JOB_DESCRIPTION]->(:JobDescription {jobDescriptionId, title, text, status})

(:User {login, role, status, displayName, createdAt, createdBy, lastLoginAt})
(:Setting {key, value, updatedAt, updatedBy})
(:ApiKey {keyId, name, hash, createdAt, createdBy, lastUsedAt})
```

`:User` — реестр пользователей интерфейса: кому можно войти и с какой
ролью (пароля в нём нет). К каталогу он не относится: в выгрузку
`seed.cypher` не попадает, полный сброс каталога его не трогает, операции
над произвольным узлом (`/catalog/nodes/*`) его не видят. То же относится
к `:Setting` (переключатели раздела «Настройки») и `:ApiKey` (ключи доступа
внешних систем).

`Rule.type` задаёт направление проверки:

| type | Нарушение возникает, когда атрибут |
|---|---|
| `PROHIBITION` | **присутствует** в цели |
| `REQUIREMENT` | **отсутствует** в цели |

У `Order`, `Clause`, `Rule`, `CheckTarget` и `ViolationExample` есть свойство
`status` (`active` / `archived`). Все запросы проверки фильтруют по нему через
`coalesce(x.status, 'active')`, поэтому узлы, заведённые до появления статуса,
остаются активными.

`CheckTarget` — единственный источник истины по проверяемым атрибутам.
Промпт для модели строится из `CheckTarget.description` во время выполнения,
поэтому новый атрибут добавляется правкой графа, а не кода.

## Примеры в промпте

По умолчанию модель решает, есть ли атрибут в цели, только по его
описанию. Настройка «Примеры в промпте» добавляет под атрибутом примеры
из каталога — до заданного настройкой «Примеров на атрибут» числа каждого вида:

```
- "проект" — в цели явно назван проект, программа или инициатива…
    есть: «В рамках проекта «Альфа» разработать API для интеграции до 01.06.2025»
    нет: «Реализовать требования по автоматизации процесса в системе 1С:KPI»
```

Пример в каталоге относится к правилу, а промпту нужен ответ про атрибут,
и однозначен он не всегда:

| Правило | Пример | Что говорит про атрибуты правила |
|---|---|---|
| требование | корректный | все присутствуют — «есть» |
| требование | нарушение | не хватает хотя бы одного; идёт в «нет», только если атрибут у правила один |
| запрет | корректный | ни одного нет — «нет» |
| запрет | нарушение | есть хотя бы один; идёт в «есть», только если атрибут у правила один |

Неоднозначные примеры в промпт не попадают. Исправить ошибку модели при
включённой настройке можно, не переписывая описание атрибута: достаточно
добавить правилу пример — ту цель, на которой она ошиблась. Эффект
настройки измеряется [проверкой примеров](web-ui.md#проверка-примеров-на-модели).

## Разграничение по подразделениям

Какое правило в каком подразделении действует — часть приказа, поэтому
это хранится в графе, а не в коде и не в вызывающей системе. Подразделения
плоские, без иерархии; у каждого есть название и `departmentId` — тот
идентификатор, который кадровая система передаёт в запросе проверки.

| Связь от правила | Что означает |
|---|---|
| нет связей | правило действует для всех подразделений |
| `ONLY_IN` | правило действует только в перечисленных подразделениях |
| `EXCEPT_IN` | в этом подразделении правило не применяется |

Пример: проект обязателен только в УЦТ и АГД — у правила две связи
`ONLY_IN`. Для цели любого другого подразделения это правило не
проверяется вовсе.

У исключения (`EXCEPT_IN`) три свойства:

| Свойство | Назначение |
|---|---|
| `basis` | код пункта приказа, который вводит исключение; попадает в ответ проверки как основание |
| `status` | `active` — действует; `candidate` — ждёт утверждения и в вердикте не участвует |
| `note` | примечание: откуда взялась договорённость |

Кандидаты — это допущения, которые сложились на практике внутри
подразделения, но приказом не закреплены. Они заводятся тем же механизмом,
чтобы не теряться: нарушение по такому правилу остаётся нарушением, но
в ответе помечается, что есть неутверждённое исключение. Когда владелец
приказа утверждает исключение, ему проставляют основание и статус `active`.
Действующему исключению основание обязательно — без него API его не примет.

### Если подразделение неизвестно

Отказ в сторону строгости, как и при сбое модели: если `department_id`
не передан, не найден в графе или подразделение в архиве, применяются
**все** правила — включая ограниченные через `ONLY_IN` — и не учитывается
ни одно исключение. Причина пишется в `notes`. Неизвестное подразделение
не должно получать более мягкий набор правил, чем известное.

По той же причине ограничение `ONLY_IN` учитывается независимо от статуса
подразделения, а удалить подразделение, на которое ссылаются правила,
нельзя: иначе ограничение исчезло бы вместе со связью, и правило молча
стало бы действовать для всех.

## Должностные инструкции

Часть требований нельзя проверить по одному тексту цели. Пункт 3.5 запрещает
цели, дублирующие должностные обязанности, — для этого цель нужно сравнить
с должностными инструкциями.

Инструкции хранятся у подразделения (`:JobDescription`, загружаются в разделе
«Подразделения»). Атрибут со свойством `source = "job_descriptions"` в общий
промпт извлечения не попадает: агент отдельным запросом сравнивает цель со
всеми действующими инструкциями подразделения, а критерием служит
`CheckTarget.description`. Дальше атрибут участвует в правилах как обычный:
пункт 3.5 — это запрет (`PROHIBITION`) на таком атрибуте, со своими
исключениями, областью действия и примерами. Найденные обязанности
возвращаются в нарушении полем `matched_duties`.

При загрузке или правке текста инструкции модель один раз выписывает из него
список обязанностей (`JobDescription.duties`). Цель сравнивается с этим
списком, а не с полным текстом: запрос короче в разы, и все должности
подразделения помещаются в один запрос. Список сразу показывается редактору
на проверку (`dutiesReviewed`); неподтверждённый список уже участвует
в проверках и виден в «Замечаниях». Если модель при загрузке не ответила,
инструкция остаётся без списка и сравнение идёт по полному тексту.

Пунктов, опирающихся на инструкции, может быть несколько: каждому — свой
атрибут со своим критерием. Каждый такой атрибут — отдельный запрос к модели
на цель; он идёт одновременно с извлечением обычных атрибутов. В один запрос
уходит до `JOB_TEXT_MAX_CHARS` символов (по умолчанию 24000 — под окно vLLM
`VLLM_MAX_MODEL_LEN` в 16384 токена; меняйте их вместе); что не поместилось —
уходит следующим запросом, а отдельный текст длиннее предела сравнивается
не целиком, о чём пишется в `notes`.

Сравнение выполняется, только если в подразделении действует правило на
таком атрибуте. Если сравнить не удалось — подразделение неизвестно,
инструкции не загружены, модель не ответила, — цель не разрешается:
при отсутствии других нарушений статус `NEEDS_MANUAL_REVIEW`, причина
в `notes`. Подразделения без инструкций показывает диагностика.

## Нагрузка: очередь к модели и кэш

Узкое место проверки — модель. Одновременных запросов к ней на весь сервис —
не больше `LLM_MAX_CONCURRENCY`; остальные ждут в очереди внутри API
(`api/metrics.py`). Ожидание в очереди не расходует таймаут модели, поэтому
под нагрузкой цели не уходят в «ручную проверку» из-за таймаутов. Пакетной
проверке недоступны `LLM_INTERACTIVE_RESERVE` слотов: массовый прогон не
останавливает ручные проверки.

Ответ модели ограничен JSON-схемой (guided decoding vLLM) и длиной
(`LLM_MAX_TOKENS`): имена атрибутов вне словаря и ответы «мимо формата»
исключены, а сбившаяся модель не держит слот. Если сервер схему не принимает,
API сам переходит на разбор свободного текста (`LLM_JSON_MODE=0` — выключить
заранее).

Ответ на ту же цель того же подразделения берётся из кэша в памяти
(настройки «Кэш ответов» и «Срок жизни кэша»). Любая правка каталога через API кэш сбрасывает;
правка базы в обход API (миграция, Neo4j Browser) станет видна проверкам
не позже чем через срок жизни кэша либо после перезапуска `api`. Сбои
(`NEEDS_MANUAL_REVIEW`) не кэшируются.

## История проверок и мониторинг

Каждая проверка оставляет запись `(:CheckRecord {at, ms, status, departmentId,
login, mode, batchId, cached, llmCalls, llmMs, queueMs, violations, goal})`.
Записи пишутся фоновым потоком пачками (`api/history.py`) и хранятся
столько дней, сколько задано настройкой «Срок хранения истории». Как и `:User`, к каталогу они не относятся:
в выгрузку не попадают, полный сброс каталога их не трогает.

Раздел «Мониторинг» (только администратор) показывает текущую очередь и
нагрузку — они живут в памяти процесса и после перезапуска начинаются с
нуля, — а также средние показатели за период и историю из графа. Раздел
«Граф» рисует каталог узлами и связями и доступен всем ролям.

### Описание атрибута — обязательно

У атрибута без `description` модель получает в промпте только имя, без
критерия, и системно перестаёт его распознавать. Внешне это выглядит как
«правило срабатывает всегда»: атрибут не найден → требование не выполнено.
Поэтому `/ready` отдаёт 503, пока есть атрибуты без описания.

### Написание имён

Уникальность `CheckTarget.name` не защищает от двойников: для Neo4j
`«срок исполнения»` и `«срок_исполнения»` — разные узлы. Если правило висит
на одном написании, а модель вернула другое, получается ложное нарушение.

Защита двухслойная: агент сопоставляет имена по нормализованной форме
(регистр, пробелы, дефисы, «ё») и при совпадении засчитывает **все**
написания сразу, а `/ready` и поле `notes` в ответе сообщают о самих
дублях, чтобы их свели к одному узлу, а не жили с ними.
