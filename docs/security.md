# Доступ и безопасность

[← README](../README.md)

Интерфейс и API доступны только после входа. Кто пользователь — решает
каталог организации (LDAP / Active Directory), что ему можно — роль,
назначенная в самом интерфейсе.

## Как устроен вход

1. Пользователь вводит доменный логин и пароль в форме входа.
2. API проверяет, что логину назначена роль (реестр `:User` в Neo4j или
   список `AUTH_ADMIN_LOGINS`). Логин без роли до каталога не доходит.
3. API подключается к каталогу **именем и паролем самого пользователя**
   (прямой bind, имя строится по `LDAP_USER_TEMPLATE`). Сервисной учётки
   нет, пароли API не хранит и в журнал не пишет.
4. При успехе выдаётся сессия: случайный токен в cookie.

Отказ во всех случаях одинаковый — «неверный логин или пароль, либо доступ
не назначен»: форма не подсказывает, какие логины существуют.

## Роли

| Роль | Что может |
|---|---|
| Читатель (`viewer`) | смотреть каталог и замечания, проверять цели |
| Редактор (`editor`) | плюс создавать и править приказы, пункты, правила, примеры, атрибуты, подразделения, отправлять в архив и возвращать |
| Администратор (`admin`) | плюс удалять навсегда, запускать ремонт идентификаторов, управлять пользователями |

Роли назначаются в разделе «Пользователи» (виден только администратору):
логин — тот же, что в домене, без домена. Смена роли, блокировка и удаление
действуют сразу, а не после истечения сессии: роль читается при каждом
запросе. Свою роль администратор изменить не может — так нельзя случайно
остаться без доступа.

**Первый администратор** задаётся в `.env`: `AUTH_ADMIN_LOGINS=i.ivanov`.
Перечисленные там логины — администраторы всегда, в интерфейсе они помечены
«задан в настройках сервера» и не редактируются.

Права проверяет API на каждом запросе; скрытые в интерфейсе кнопки — только
удобство. Новый маршрут без проверки прав роняет тест
`test_every_route_requires_a_session`.

## Что защищено и чем

| Угроза | Защита |
|---|---|
| Доступ без входа | все маршруты, кроме `/health`, `/ready` и входа, требуют сессию; `/ready` наружу не проксируется |
| Кража сессии скриптом страницы | cookie `HttpOnly`; на сервере хранится только SHA-256 токена |
| Перехват в сети | cookie с флагом `Secure` (TLS завершается на внешнем прокси), заголовок HSTS; к каталогу — только LDAPS или STARTTLS с проверкой сертификата |
| CSRF | cookie `SameSite=Strict`; изменяющие запросы обязаны нести `X-Requested-With`; CORS не настроен — интерфейс и API на одном origin |
| Перебор паролей | 5 неудачных входов подряд блокируют логин на 15 минут, 30 — адрес; незарегистрированные логины в каталог не отправляются |
| Анонимный bind | пустой пароль отклоняется до обращения к каталогу |
| Подстановка в запрос к каталогу | логин — только латиница, цифры, `.`, `-`, `_` |
| Брошенная сессия | выход после 30 минут простоя, предельный срок — 12 часов; выход закрывает сессию на сервере |
| Повышение прав через редактор свойств | операции `/catalog/nodes/*` видят только узлы каталога, узлы `:User` им недоступны |
| Фишинговая ссылка | адрес API нельзя подменить параметром страницы (`?api=` убран) |
| Встраивание и чужие скрипты | `Content-Security-Policy`, `X-Frame-Options: DENY`, `nosniff`, `Referrer-Policy` |
| Обход интерфейса | Neo4j, vLLM и API слушают только `127.0.0.1`; наружу опубликован один порт интерфейса |
| Разведка API | Swagger выключен, включается `ENABLE_DOCS=1` |

## Журнал аудита

Каждое изменение, вход, выход и отказ в правах — JSON-строка логгера
`audit` в логе API:

```bash
docker compose logs api | grep ' audit: '
```

```json
{"ts": "2026-10-02T09:14:03+00:00", "event": "login_ok", "login": "i.ivanov", "role": "editor", "ip": "10.1.2.3"}
{"ts": "2026-10-02T09:15:40+00:00", "event": "request", "login": "i.ivanov", "role": "editor", "ip": "10.1.2.3",
 "method": "PATCH", "path": "/catalog/nodes/4:…:12/properties", "status": 200, "ms": 31, "body": "{\"properties\": …}"}
{"ts": "2026-10-02T09:16:02+00:00", "event": "login_failed", "login": "p.petrov", "ip": "10.1.2.9", "reason": "bad_credentials"}
```

Для изменений каталога пишется тело запроса (первые 2000 символов) —
видно, что именно поменяли. Тела запросов к `/auth` и тексты проверяемых
целей в журнал не попадают. Чтение каталога не журналируется.

Причины отказа во входе: `bad_credentials`, `not_registered` (роль не
назначена или пользователь заблокирован), `bad_login_format`,
`directory_unavailable`; событие `login_throttled` — сработала блокировка.

## Настройка на сервере

```dotenv
LDAP_URL=ldaps://dc.corp.local:636
LDAP_USER_TEMPLATE={login}@corp.local
LDAP_CA_FILE=/certs/corp-ca.pem      # файл положить в ./certs рядом с compose
AUTH_ADMIN_LOGINS=i.ivanov
TRUSTED_PROXY=10.0.0.5               # адрес прокси, на котором завершается TLS
```

- **TLS до пользователя** завершается на внешнем прокси, который
  направляет запросы на порт 3000. Cookie сессии помечена `Secure`,
  поэтому по HTTP с другого компьютера войти не получится — это намеренно.
- **`TRUSTED_PROXY`** — адрес этого прокси. Из его `X-Forwarded-For`
  берётся адрес клиента для журнала и ограничения перебора; без настройки
  все пользователи будут видны под адресом прокси и разделят один счётчик
  неудачных входов.
- **Сертификат каталога** проверяется всегда. Если домен подписан своим
  центром сертификации, без `LDAP_CA_FILE` вход будет отвечать
  «каталог недоступен», а в логе API появится причина.
- **Neo4j Browser и bolt** снаружи закрыты. С рабочего места:
  `ssh -L 7474:localhost:7474 -L 7687:localhost:7687 <сервер>`.

### Стенд без каталога

`AUTH_BACKEND=static` проверяет пароль по записи в `AUTH_STATIC_USERS`
(`логин:запись`, через запятую) — так настроен `.env` в репозитории.
Запись — PBKDF2-хеш, а не пароль:

```bash
docker compose run --rm api python auth.py hash
```

Роли при этом назначаются так же, через реестр и `AUTH_ADMIN_LOGINS`.
Режим только для стенда: при запуске API пишет об этом предупреждение.

## Ограничения

- Сессии и счётчики неудачных входов живут в памяти процесса API:
  перезапуск API требует войти заново, а uvicorn должен работать одним
  процессом (так задано в `api/Dockerfile`).
- Внешним системам вход по ключу не предусмотрен: `/check-goal` и
  `/check-goals` работают только в сессии пользователя.
- Проверяется только пароль в каталоге; членство в группах домена на роль
  не влияет. Уволенному сотруднику достаточно отключить учётку в домене —
  войти он не сможет, но запись в реестре останется до удаления.
- Блокировка по числу неудачных входов позволяет постороннему на 15 минут
  закрыть вход известному логину; действующие сессии при этом не рвутся.
