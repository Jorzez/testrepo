# Goal Checker Agent

Проверка формулировки цели на соответствие действующим приказам.
Требования хранятся графом в Neo4j, языковая модель (vLLM) определяет,
какие проверяемые атрибуты присутствуют в тексте цели, Cypher-запросы
находят сработавшие запреты и невыполненные требования.

## Архитектура

```
web (nginx :3000) ──► api :8080           редактор каталога и проверка целей
api (FastAPI :8080) ─┬─► Neo4j :7687      каталог, поиск нарушений
                     └─► vLLM :8000       извлечение атрибутов из цели
seeder (разовый)   ──► Neo4j              схема + миграции из neo4j/init/
export_graph.py    ◄── Neo4j              выгрузка графа обратно в seed.cypher
```

Веб-интерфейс общается только с API: прямого подключения к Neo4j из браузера
больше нет, вместе с ним из кода страницы ушёл и пароль базы.

## Модель данных

```
(:Order {orderId, number, title, date, status})
  -[:CONTAINS]->   (:Clause {clauseId, code, text})
  -[:DEFINES]->    (:Rule {ruleId, type, description, checkInstruction})
  -[:APPLIES_TO]-> (:CheckTarget {name, description})

(:Rule)-[:HAS_EXAMPLE]->(:ViolationExample {exampleId, text, isViolation})
(:Clause)-[:REFERENCES]->(:Clause)
```

`Rule.type` задаёт направление проверки:

| type | Нарушение возникает, когда атрибут |
|---|---|
| `PROHIBITION` | **присутствует** в цели |
| `REQUIREMENT` | **отсутствует** в цели |

У `Order`, `Clause`, `Rule`, `CheckTarget` и `ViolationExample` есть свойство
`status` (`active` / `archived`). Все запросы проверки фильтруют по нему через
`coalesce(x.status, 'active')`, поэтому узлы, заведённые до появления статуса,
остаются активными.

`CheckTarget` — единственный источник истины по проверяемым атрибутам.
Промпт для модели строится из `CheckTarget.description` во время выполнения,
поэтому новый атрибут добавляется правкой графа, а не кода.

### Описание атрибута — обязательно

У атрибута без `description` модель получает в промпте только имя, без
критерия, и системно перестаёт его распознавать. Внешне это выглядит как
«правило срабатывает всегда»: атрибут не найден → требование не выполнено.
Поэтому `/ready` отдаёт 503, пока есть атрибуты без описания.

### Написание имён

Уникальность `CheckTarget.name` не защищает от двойников: для Neo4j
`«срок исполнения»` и `«срок_исполнения»` — разные узлы. Если правило висит
на одном написании, а модель вернула другое, получается ложное нарушение.

Защита двухслойная: агент сопоставляет имена по нормализованной форме
(регистр, пробелы, дефисы, «ё») и при совпадении засчитывает **все**
написания сразу, а `/ready` и поле `notes` в ответе сообщают о самих
дублях, чтобы их свели к одному узлу, а не жили с ними.

## Запуск

В `.env` должны быть заданы `NEO4J_PASSWORD`, `VLLM_MODEL` и `HF_TOKEN`
(полный список — в таблице ниже).

```bash
docker compose up -d --build
```

Порядок подъёма задан через `depends_on`: `neo4j` → `seeder` → `api`.
API стартует только после того, как сидер успешно отработал, а vLLM
прошёл healthcheck (загрузка весов 8B-модели занимает несколько минут,
поэтому у неё `start_period: 900s`).

| Сервис | Адрес |
|---|---|
| API | http://localhost:8080 |
| Swagger | http://localhost:8080/docs |
| Редактор каталога | http://localhost:3000 |
| Neo4j Browser | http://localhost:7474 |

Для запуска без GPU укажите внешний OpenAI-совместимый эндпоинт
через `VLLM_URL` и поднимайте стек без сервиса `vllm`.

## Эндпоинты

### Пакетная проверка

```bash
curl -s localhost:8080/check-goals \
  -H 'Content-Type: application/json' \
  -d '[{"goal": "Снизить долю просроченных заявок до 5% к 31.12.2025", "id": "kpi-1"},
       {"goal": "Улучшить работу с заявками", "id": "kpi-2"}]'
```

Вход — массив объектов `{"goal": "...", "id": "..."}`; `id` необязателен
и возвращается как передан (или `null`). Ответ:

```json
{
  "results": [ { "id": "kpi-1", "goal": "...", "status": "...", "allowed": true,
                 "detected_attributes": [], "violations": [], "notes": [] } ],
  "summary": { "total": 2, "allowed": 1, "violations": 1, "manual_review": 0 }
}
```

Порядок ответов совпадает с порядком входа. Словарь атрибутов читается один
раз на весь пакет, обращения к модели идут параллельно (`BULK_MAX_WORKERS`,
по умолчанию 4) — узкое место именно они. Сбой одной цели не роняет пакет:
она получает `NEEDS_MANUAL_REVIEW`, остальные проверяются как обычно.
Размер пакета ограничен `MAX_GOALS_PER_REQUEST` (по умолчанию 200), при
превышении — `413`.

### Прочее

```bash
curl -s localhost:8080/health          # liveness
curl -s localhost:8080/ready           # readiness + диагностика графа
curl -s localhost:8080/check-targets   # словарь проверяемых атрибутов

curl -s localhost:8080/check-goal \
  -H 'Content-Type: application/json' \
  -d '{"goal": "Снизить долю просроченных заявок до 5% к 31.12.2025"}'
```

`/ready` отдаёт 503 и список `problems`, если Neo4j недоступен, граф пуст,
есть двойники атрибутов, атрибуты без описания, атрибуты без правил или
правила без атрибутов — то есть в любой ситуации, когда проверка целей
будет молча неполной.

Ответ `/check-goal`:

```json
{
  "goal": "...",
  "status": "ALLOWED | VIOLATIONS_FOUND | NEEDS_MANUAL_REVIEW",
  "allowed": false,
  "detected_attributes": ["срок_исполнения", "измеримость"],
  "violations": [
    {
      "order_number": "ПР-01",
      "order_title": "О порядке постановки целей",
      "clause_code": "1.1",
      "clause_text": "...",
      "rule_id": "R-1.1",
      "rule_text": "...",
      "check_instruction": "Проверь, указан ли в тексте цели проект...",
      "violation_type": "MISSING_REQUIREMENT",
      "attribute": "проект",
      "example_kind": "correct",
      "examples": ["..."]
    }
  ],
  "notes": []
}
```

`notes` — не декоративное поле. Туда попадают атрибуты, которых нет
в словаре графа, и обнаруженные двойники написаний: это причины, по
которым результат проверки может быть неполным.

Оба типа нарушений возвращаются с одинаковым набором полей; различать их
следует по `violation_type` и `example_kind` (`violation` — так делать нельзя,
`correct` — образец правильной формулировки).

### Режим отказа: fail-closed

Если извлечь атрибуты не удалось (модель недоступна, вернула не JSON,
словарь `CheckTarget` пуст), ответ будет `status: NEEDS_MANUAL_REVIEW`
и `allowed: false`, а причина — в `notes`. Проверка соответствия
никогда не «разрешает» цель из-за собственного сбоя.

## Веб-интерфейс

`http://localhost:3000` — редактор каталога. Четыре вкладки:

| Вкладка | Что делает |
|---|---|
| Приказы и пункты | дерево приказ → пункт → правило → атрибуты и примеры; создание, правка, перенос, архивирование и удаление на каждом уровне; поиск по всему дереву |
| | Приказы и пункты сворачиваются независимо, по умолчанию свёрнуты. При поиске совпавшие узлы раскрываются сами. |
| Атрибуты | словарь `:CheckTarget` с описаниями; видно, какие правила ссылаются на атрибут и у каких нет описания |
| Проверка цели | прогон формулировки через `/check-goal` с разбором нарушений |
| Диагностика | что мешает проверкам работать честно, с переходом к конкретному объекту |

Адрес API по умолчанию — тот же хост, порт 8080; переопределяется параметром
`?api=http://host:port`, поэтому интерфейс работает и через SSH-туннель.

### Адресация узлов

Узлы адресуются по `elementId()` Neo4j, а не по бизнес-ключам. Это не деталь
реализации: у данных, заведённых до появления схемы, `orderId` может
отсутствовать, и раскрытие карточки по такому ключу молча не работало.
`elementId` есть у любого узла всегда.

Бизнес-ключи (`orderId`, `clauseId`, `ruleId`, `exampleId`) остаются
редактируемыми свойствами — они нужны выгрузке в `seed.cypher`, которая
строит по ним `MERGE`. Узел без ключа помечается плашкой в интерфейсе
и попадает в диагностику с кнопкой автоматической починки.

### Что можно менять

Полный цикл на каждом уровне:

| Объект | Операции |
|---|---|
| Приказ | создать, править (номер, заголовок, дата, orderId), архив, удалить, произвольные свойства |
| Пункт | создать, править (номер, текст, clauseId), перенести в другой приказ, перекрёстные ссылки `REFERENCES`, архив, удалить, произвольные свойства |
| Правило | создать, править (тип, формулировка, инструкция, ruleId), привязка к атрибутам, перенести в другой пункт, архив, удалить, произвольные свойства |
| Пример | создать, править (текст, вид, exampleId), архив, удалить, произвольные свойства |
| Атрибут | создать, править (имя, описание), архив, удалить, произвольные свойства |

Все операции над приказом, пунктом, правилом и атрибутом собраны в меню «⋯»
справа от объекта — иначе строка кнопок оказывалась шире содержимого.
У примеров кнопки остались на виду: их три и они самые частые.

Пункт «Свойства» открывает редактор произвольных свойств узла: можно
добавить своё поле, изменить тип (строка, число, да/нет, дата) или удалить
свойство. Ключевые свойства проверяются на уникальность. `status` меняется
только кнопками «В архив» / «Вернуть» — у него своя логика.

### Удаление — двухшаговое

«Удалить» никогда не означает «потерять с первого клика»:

1. **В архив** — узел получает `status: "archived"`, выпадает из проверок
   (все запросы фильтруют по статусу), но остаётся в графе. Обратимо кнопкой «Вернуть».
2. **Удалить навсегда** — физическое удаление вместе со всем, что без узла
   теряет смысл. Предварительное архивирование не требуется, но диалог
   подтверждения показывает, что именно уйдёт (сколько пунктов, правил,
   примеров), и это необратимо.

В API это разные режимы: `DELETE /catalog/nodes/{nodeId}` удаляет только
архивированный узел, `?force=true` — любой. Интерфейс всегда передаёт
`force=true`, потому что подтверждение уже спрошено явно.

Единственное, что `force` не обходит: атрибут, на который ссылаются правила,
не удаляется никогда — иначе правила повиснут без привязки и молча
перестанут срабатывать.

Архивирование любого узла на пути `Приказ → Пункт → Правило → Атрибут`
отключает всё, что ниже: проверка идёт по цепочке целиком.
Атрибут нельзя удалить, пока на него ссылается правило.

### Защита от двойников на входе

При создании атрибута имя сравнивается по нормализованной форме, поэтому
завести «срок исполнения» рядом с «срок_исполнения» через интерфейс
невозможно — API вернёт 409 с указанием существующего написания.

## Диагностика

Вкладка «Диагностика» и `GET /catalog/diagnostics` отвечают на один вопрос:
как дефект данных проявится снаружи. Каждая проблема объясняется текстом,
перечисляет конкретные объекты и даёт кнопку «Показать» — переход к объекту
в каталоге с подсветкой.

| Проверка | Уровень | Как проявляется |
|---|---|---|
| Пустой словарь атрибутов | ошибка | любая проверка возвращает `NEEDS_MANUAL_REVIEW` |
| Атрибуты-двойники по написанию | ошибка | ложные нарушения: правило на одном узле, ответ модели про другой |
| Атрибуты без описания | ошибка | модель системно не распознаёт атрибут, правило срабатывает всегда |
| Правила без привязки к атрибуту | ошибка | правило не участвует ни в одном запросе |
| Узлы без идентификатора | ошибка | невозможна выгрузка в `seed.cypher` — **чинится кнопкой** |
| Атрибуты без правил | предупреждение | тратят контекст модели, ни на что не влияя |
| Пункты без правил, приказы без пунктов | предупреждение | текст есть, проверки нет |
| Примеры не того вида, что нужен правилу | предупреждение | поле `examples` в ответе остаётся пустым |
| Повторяющиеся номера пунктов | предупреждение | нарушения невозможно различить в ответе |
| Правила без примеров | справочно | ответ проверки суше |
| Архивные узлы | справочно | не участвуют в проверках, но попадают в выгрузку |

Ошибки блокируют готовность: пока они есть, `/ready` отдаёт 503.
Предупреждения и справочные пункты — нет. Значок с числом проблем виден
на самой вкладке.

## Эндпоинты каталога

```
GET    /catalog/tree?include_archived=false     всё дерево одним ответом
GET    /catalog/check-targets                   словарь атрибутов
GET    /catalog/clauses                         плоский список пунктов
GET    /catalog/diagnostics                     развёрнутая диагностика

GET    /catalog/nodes/{nodeId}                  все свойства узла
PATCH  /catalog/nodes/{nodeId}/properties       правка любых свойств (null удаляет)
POST   /catalog/nodes/{nodeId}/status           active / archived
GET    /catalog/nodes/{nodeId}/descendants      что уйдёт при удалении
DELETE /catalog/nodes/{nodeId}                  физическое удаление

POST   /catalog/orders                          POST /catalog/clauses
POST   /catalog/rules                           POST /catalog/examples
POST   /catalog/check-targets

PUT    /catalog/rules/{nodeId}/targets          привязка правила к атрибутам
PUT    /catalog/clauses/{nodeId}/references     перекрёстные ссылки
POST   /catalog/clauses/{nodeId}/move           перенос в другой приказ
POST   /catalog/rules/{nodeId}/move             перенос в другой пункт
POST   /catalog/repair-identifiers              проставить недостающие ключи

DELETE /catalog/nodes/{nodeId}?force=true       удалить без архивирования
```

`404` — узла нет, `409` — операция противоречит состоянию графа
(двойник по написанию, удаление неархивированного узла, используемый атрибут,
занятый бизнес-ключ), `422` — не прошла валидация схемы.

## Данные: база — источник истины

`neo4j/init/seed.cypher` содержит только схему (ограничения и индексы) и
маркер `// ---------- Данные ----------`. Сами приказы не пишутся в файл
руками — они выгружаются из живой базы:

```bash
docker compose exec api python export_graph.py --output /init/seed.cypher
```

Скрипт снимает приказы, пункты, правила, атрибуты, примеры и связи и
дописывает в файл идемпотентный `MERGE`-скрипт со стабильным порядком
строк. После этого `docker compose up` воспроизводит граф один в один,
а `git diff` показывает, что именно поменялось в нормативке.

Посмотреть выгрузку, ничего не записывая:

```bash
docker compose exec api python export_graph.py --stdout
```

### Полный сброс и загрузка

`neo4j/init/reset_and_load.cypher` удаляет все узлы и заводит каталог заново —
уже со всеми полями, которых требуют текущие проверки: бизнес-ключи, статусы,
описания атрибутов, примеры нужного вида.

```bash
docker compose exec neo4j neo4j-admin database dump neo4j --to-stdout > backup.dump
docker compose run --rm -e SEED_FILE=/init/reset_and_load.cypher seeder
curl -s localhost:8080/ready | python3 -m json.tool     # ожидается ready
docker compose exec api python export_graph.py --output /init/seed.cypher
```

Скрипт удаляет данные — дамп перед запуском обязателен. Полная альтернатива,
если не жаль тома целиком: `docker compose down && docker volume rm <проект>_neo4j_data`.

В скрипте заведено то, что видно по ответам API: ПР-01, пункты 1.1 и 2.4.
Остальную нормативку добавляйте по закомментированному шаблону в конце файла
или через интерфейс — он делает ровно то же самое.

### Миграции

Разовые правки данных лежат в `neo4j/init/migrations/` и запускаются
тем же сидером через `SEED_FILE`:

```bash
# перед любой миграцией — дамп
docker compose exec neo4j neo4j-admin database dump neo4j --to-stdout > backup.dump

docker compose run --rm \
  -e SEED_FILE=/init/migrations/001_cleanup_demo_data.cypher seeder
docker compose run --rm \
  -e SEED_FILE=/init/migrations/002_check_target_descriptions.cypher seeder
```

| Миграция | Что делает |
|---|---|
| `001_cleanup_demo_data` | удаляет демо-приказы ПР-2024-15 / ПР-2024-22, сводит двойники `CheckTarget`, чистит осиротевшие атрибуты и примеры |
| `002_check_target_descriptions` | проставляет описания атрибутам `проект` и `срок_исполнения`; шаблон для остальных внутри файла |

Миграции правят существующую базу, не удаляя её. Если проще начать с чистого
листа — используйте `reset_and_load.cypher` выше.

### Порядок приведения базы в порядок

```bash
docker compose exec neo4j neo4j-admin database dump neo4j --to-stdout > backup.dump
docker compose run --rm -e SEED_FILE=/init/migrations/001_cleanup_demo_data.cypher seeder
docker compose run --rm -e SEED_FILE=/init/migrations/002_check_target_descriptions.cypher seeder
curl -s localhost:8080/ready | python3 -m json.tool   # что ещё осталось починить
# дописать описания оставшимся атрибутам, затем зафиксировать состояние:
docker compose exec api python export_graph.py --output /init/seed.cypher
git diff neo4j/init/seed.cypher
```

## Проверка Cypher

Юнит-тесты подменяют драйвер Neo4j, поэтому текст запроса в них никогда не
разбирается: запрос с ошибкой области видимости проходит весь набор тестов
и падает только у пользователя. Ровно так сломалось удаление узлов —
переменная использовалась в `RETURN` после `WITH`, который её не пронёс.

`api/verify_cypher.py` закрывает этот класс ошибок:

```bash
cd api
python verify_cypher.py             # разбор областей видимости, база не нужна
python verify_cypher.py --explain   # плюс EXPLAIN каждого запроса на живой базе
```

Первый режим собирает все Cypher-строки проекта (константы модулей и литералы
внутри функций) и ищет переменные, использованные вне области видимости.
Он же входит в набор тестов (`tests/test_cypher.py`), поэтому запускается
на каждом прогоне.

Второй режим прогоняет `EXPLAIN` каждого запроса на живой Neo4j: полноценный
разбор и планирование средствами самой СУБД, без выполнения. Это единственный
способ поймать всё, что зависит от версии Neo4j.

## Тесты

```bash
cd api
pip install -r requirements-dev.txt
pytest
```

Тесты не требуют ни Neo4j, ни vLLM — внешние зависимости подменяются.
Покрыты: разбор ответа модели (блоки `<think>`, markdown-ограждения,
мусор), сопоставление имён атрибутов при расхождении написания,
поведение fail-closed, разбиение Cypher-скрипта, идемпотентность и
стабильность выгрузки, диагностика в `/ready`, сборка дерева каталога,
запрет на двойников и на удаление неархивированных узлов — то есть ровно
те места, где расхождение схемы и кода уже приводило к молчаливым отказам.

Интерфейс отдельно проверен браузерным прогоном (Playwright) на данных
без бизнес-ключей — той самой конфигурации, на которой карточка приказа
не раскрывалась: раскрытие, полный цикл по примерам, редактор произвольных
свойств, правка ключей, переход из диагностики к объекту, автопочинка
идентификаторов, перенос пункта, экранирование ввода, независимое
сворачивание пунктов, сбор действий в меню, соотношение размеров меню
и кнопки, удаление активного пункта без предварительного архивирования.

## Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|

| `VLLM_MODEL` | — | имя модели для vLLM |
| `HF_TOKEN` | — | токен Hugging Face для загрузки весов |
| `VLLM_IMAGE` | `vllm/vllm-openai:latest` | образ vLLM, рекомендуется зафиксировать тег |

| `LOG_LEVEL` | `INFO` | уровень логирования |

## Известные ограничения

- `/check-goal` и все эндпоинты `/catalog/*` не аутентифицированы и не
  ограничены по частоте. Редактор каталога доступен любому, кто открыл
  страницу, — до выхода за пределы доверенной сети нужна авторизация.
- Текст цели попадает в промпт без экранирования — возможна prompt injection.
- Агент засчитывает атрибут по нормализованному имени, но это лечение
  симптома: двойники в графе всё равно нужно сводить, иначе часть правил
  останется на «мёртвом» узле.
- Версии Python-зависимостей зафиксированы вручную; для полной
  воспроизводимости стоит перейти на lock-файл (`pip-compile`, `uv lock`).
