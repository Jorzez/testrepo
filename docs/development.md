## Проверка Cypher

Юнит-тесты подменяют драйвер Neo4j, поэтому текст запроса в них никогда не
разбирается: запрос с ошибкой области видимости проходит весь набор тестов
и падает только у пользователя. Ровно так сломалось удаление узлов —
переменная использовалась в `RETURN` после `WITH`, который её не пронёс.

`api/verify_cypher.py` закрывает этот класс ошибок:

```bash
cd api
python verify_cypher.py             # разбор областей видимости, база не нужна
python verify_cypher.py --explain   # плюс EXPLAIN каждого запроса на живой базе
```

Первый режим сам находит модули, которые ходят в Neo4j, собирает все их
Cypher-строки (константы модулей и литералы внутри функций) и ищет
переменные, использованные вне области видимости, в том числе обращения
к переменной, которая в запросе нигде не объявлена. Новый модуль с
запросами в список вносить не нужно. Режим входит в набор тестов
(`tests/test_cypher.py`), поэтому запускается на каждом прогоне; `--explain`
в тестах не запускается — только руками на живой базе.

Второй режим прогоняет `EXPLAIN` каждого запроса на живой Neo4j: полноценный
разбор и планирование средствами самой СУБД, без выполнения. Это единственный
способ поймать всё, что зависит от версии Neo4j.

## Тесты

```bash
cd api
python3.12 -m venv .venv && . .venv/bin/activate   # после смены зависимостей — пересоздать
pip install -r requirements-dev.txt
pytest
```

Тесты не требуют ни Neo4j, ни vLLM — внешние зависимости подменяются,
в Neo4j тесты не ходят. От окружения они не зависят: `conftest.py` убирает
переменные, экспортированные из `.env`, и выключает фоновые потоки (запись
истории, сверку версии каталога). Время кэшей тесты двигают через
`metrics._now`, а не подменой часов всего процесса.
Покрыты: разбор ответа модели (блоки `<think>`, markdown-ограждения,
мусор), сопоставление имён атрибутов при расхождении написания,
поведение fail-closed, разбиение Cypher-скрипта, идемпотентность и
стабильность выгрузки, диагностика в `/ready`, сборка дерева каталога,
запрет на двойников и на удаление неархивированных узлов — то есть ровно
те места, где расхождение схемы и кода уже приводило к молчаливым отказам.
Кэши, очередь к модели и версия каталога — в `tests/test_metrics.py`.

Два теста сторожат развёртывание:

- `tests/test_deploy.py` — каждая переменная окружения, которую читает API
  (или сидер), есть в `environment` нужного сервиса `docker-compose.yml` с тем
  же значением по умолчанию. Добавили `os.getenv` в код — добавьте строку
  в compose, иначе тест упадёт (а настройка из `.env` молча не дошла бы
  до контейнера).
- `tests/test_lock.py` — `requirements.lock` полон (sha256 у каждого пакета)
  и согласован с `requirements.txt`. После правки `requirements.txt` —
  пересобрать lock ([команда](deployment.md#зависимости-api)).

Качество распознавания эти тесты не проверяют: модель в них подменена.
Его показывает проверка примеров на настоящей модели — раздел «Замечания»,
см. [веб-интерфейс](web-ui.md#проверка-примеров-на-модели).

Вход и права — в `tests/test_auth.py`: Keycloak подменён ключом, которым
тест сам подписывает токены. Каждый маршрут без токена отвечает `401`
(новый маршрут без проверки прав роняет этот тест), матрица ролей,
отвергнутые токены (чужая подпись, другой realm, другой клиент, истёкший,
refresh вместо access), `403` вошедшему без роли, `503` при недоступном
Keycloak, отметка входа по сессии Keycloak, немедленное действие смены
роли и блокировки, журнал аудита без токенов. В остальных тестах HTTP-слоя
пользователь подменяется через `app.dependency_overrides[auth.current_user]`.

## Интерфейс

Редактор каталога — React + TypeScript на Vite, исходники в `web/`.
Нужен Node.js 22.

```bash
cd web
npm install
npm run dev:mock      # http://localhost:5173 с фейковым API — без Neo4j, vLLM и Docker
npm run dev           # то же, но с настоящим API на :8080 (прокси на тот же origin)
```

Фейковый API включает и фейковый Keycloak (`/api/idp`): кнопка «Войти»
открывает его страницу входа, дальше всё как с настоящим — код, обмен
на токен, `Authorization: Bearer`. Учётки — `admin`, `editor`, `viewer`,
пароль у всех `demo` (константа `MOCK_PASSWORD`): так видно интерфейс
каждой роли. Обучение по интерфейсу в нём показывается при первом входе
каждой учётки и до перезапуска больше не повторяется (повтор — из меню
пользователя). С настоящим API входят через Keycloak стенда из compose
(учётка `admin`, см. `.env`); адрес `localhost:5173` у его клиента уже
разрешён.

Оба режима перезагружают страницу при каждом сохранении файла. Адрес
настоящего API меняется переменной `VITE_API_TARGET`.

Фейковый API (`web/mock/backend.ts`) держит данные в памяти и повторяет
поведение настоящего, видимое интерфейсу: формы ответов, коды `202`, `401`,
`403`, `404`, `409`, `422`, `503` (режим обслуживания; у `/check-goals` —
занятая очередь пакетов с `Retry-After`, первые N запросов задаёт
`createBackend({ bulkBusy: N })`), вход и роли,
каскадное удаление, защиту от двойников. Выписка обязанностей — как у
настоящего: `202` и `dutiesStatus: "pending"`, готовый список отдаёт
следующий `GET`. Запрос из браузера без `Authorization` получает `401`;
вызовы из самих тестов без заголовков идут от имени `options.user`. Данные
сбрасываются при перезапуске. Поменяли ответ API — поправьте фейк и типы
в `web/src/api/types.ts`: у эндпоинтов нет `response_model`, поэтому OpenAPI
ответы не описывает и типы из него не генерируются. Соответствие фейка
настоящему API по кодам и формам ответов проверяет
`web/tests/mock-contract.spec.ts` (без браузера).

### Проверки интерфейса

```bash
cd web
npm run typecheck                 # TypeScript
npx playwright install chromium   # один раз
npm test                          # e2e на собранной версии
PW_CHANNEL=chrome npm test        # то же на установленном Google Chrome, без скачивания браузера
```

Каждый e2e-тест получает свой экземпляр фейкового API, пользователь в нём
уже вошёл администратором — токены фейкового Keycloak кладутся
в `sessionStorage` до загрузки страницы (другая роль — `test.use({ role: "viewer" })`)
и обучение по интерфейсу у него уже пройдено — иначе оно перекрыло бы
каждый сценарий (первый вход — `test.use({ firstLogin: true })`). Запрос
к фейковому API в обход интерфейса (`page.request`, `fetch`) делайте
с заголовками `apiHeaders()` из `tests/fixtures.ts` — без них он получит `401`.
Сценарии — те, на которых интерфейс уже ломался или которые легко сломать:
вход через Keycloak с PKCE и выход, закрытая сессия (окно «Сессия
завершена», возврат черновиков), незаметное обновление токена, отказ
вошедшему без роли, что видит читатель и редактор, управление
пользователями, обучение по интерфейсу (первый вход, состав по ролям, отметка, повтор из меню),
проверка цели с подразделением (правило «только в»), пакетная проверка
и загрузка Excel, мониторинг, настройки, советчик по графу,
матрица (состояния ячеек, «не действует»),
панель правила (область действия, примеры, описание атрибута),
мастер правила целиком и его проверки шагов, приказы на данных без
бизнес-ключей, редактор произвольных свойств, уникальность ключей, перенос
и удаление пункта, экранирование ввода, меню действий, справочники,
переходы из замечаний, автопочинка идентификаторов, недоступный API.
